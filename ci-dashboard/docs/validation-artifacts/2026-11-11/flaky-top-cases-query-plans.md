# Top flaky cases query-plan checks — 2026-11-11

Window: `2026-10-29 <= report_time < 2026-11-12` (UTC).
Plans were captured from the SQL generated by `get_flaky_top_cases`, without index hints.

## Read-only serving database baseline

`SELECT DATABASE(), VERSION()` identified `insight` on TiDB v8.5.3-serverless.
Only schema inspection and `EXPLAIN FORMAT='brief'` were performed, not ranking
execution, `EXPLAIN ANALYZE`, statistics updates, or DDL.

- All repos: `IndexRangeScan` on
  `idx_problem_case_runs_flaky_repo_report_time(flaky, repo, report_time)` estimates
  **101,290.04** historical flaky entries. The date predicates are a separate
  `Selection`, not part of its index range. This confirms the broad-scope risk.
- Repo only: that same live index can range-restrict by repo and report time
  (297.28 estimated entries). It is an extra live index absent from this
  repository's migrations; it still cannot range-restrict time with repo unset.
- Repo + `release-8.5` + job `pull-mysql-client-test`: the job-filtered query uses
  `IndexRangeScan` on `idx_ci_l1_builds_job_name(job_name)` (108.42 estimated entries)
  and a semi hash join. No builds full scan appears. The URL `IN` remains a residual
  join condition, not a normalized-URL index probe. An EXPLAIN-only trial replacing
  it with two equality `EXISTS` probes produced two job-name index scans instead of
  one, so that rewrite was not adopted without evidence of an improvement.

## Disposable exact-version migration check

A loopback-only TiDB v8.5.3 unistore instance used synthetic tables with the
repository's two existing testcase index orders and the build URL/job indexes.
There were 52,100 reports, of which 100 fell in the selected window. Statistics
were analyzed after committing the fixture data. This is a plan/DDL check, not
production latency evidence.

`033_add_flaky_report_time_index.sql` applied twice successfully. All six generated
ranking queries executed successfully and retained the expected distinct-build
counts:

| Scope | Testcase index chosen | Result counts |
| --- | --- | --- |
| All repos / all branches | `idx_problem_case_runs_flaky_report_time` | TiDB 50, PD 50 |
| TiDB / all branches | `idx_problem_case_runs_flaky_report_time` | TiDB 50 |
| All repos / release-8.5 | `idx_problem_case_runs_flaky_report_time` | TiDB 33, PD 33 |
| TiDB / release-8.5 | `idx_problem_case_runs_repo_branch_time_case` | TiDB 33 |
| TiDB / release-8.5 / unit job | `idx_problem_case_runs_repo_branch_time_case` | TiDB 33 |
| All repos / all branches / unit job | `idx_problem_case_runs_flaky_report_time` | TiDB 50, PD 50 |

The broad-scope scan excerpt was:

```text
IndexRangeScan(Build)  100.00  cop[tikv]
  table:pcr, index:idx_problem_case_runs_flaky_report_time(flaky, report_time)
  range:[1 2026-10-29 00:00:00,1 2026-11-12 00:00:00), keep order:false
```

All six plans included both date bounds in their testcase index range. The two
job-filtered plans also used the job-name index. SQLite regression tests execute
the real migration twice and assert time-bounded plans for all-repo, repo-only,
and branch-only scopes.
