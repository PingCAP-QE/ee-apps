# 资源利用率数据：保留、自动清理与防积压设计

版本：V1 生命周期设计历史；未执行线上清理，不作为当前 V2 操作步骤。
当前以 [V2 修订设计](resource-utilization-design-v2.md) §§14–17 和 V2 操作文档为准：机器日事实保留一年、Pod 为活跃有界工作集，不再保留固定周汇总。本文件下文的“两张短期表”、周封账和固定任务状态描述仅适用于 V1。
范围：Cost Insight 新增的利用率数据，首版仅腾讯云 CICD 账号 `100050658403`。
本文件是[主设计](resource-utilization-design.md)的数据生命周期约束；与早期“汇总失败先不删”的描述冲突时，以本文件为准。
规模依据：[真实 CI 规模与费用估算](tencent-utilization-validation-and-cost-estimate.md)。
2026-11-24 已确认日级持久化：资源日摘要、**repo + 稳定 Job / workload + 资源类型 / 规格**消费日摘要；不建个人利用率维度，不采磁盘使用率，不建小时表或逐 Pod 使用流水。个人归属留在原成本分账系统。北京时间 `00:30、06:30、12:30、18:30` 重算当天 / 前一天后覆盖替换；失败日期只在未过期、所需云指标仍在已验证可读窗口且必要证据可用时有界补齐，越界保留最后可信日版本并标 stale / missing（主设计 §9），不能承诺 14 天分钟重放。独立过期清理仍每 15 分钟运行。

## 1. 决策：明细是有固定寿命的工作集，不是另一份历史仓库

用户只需要历史周趋势，不需要历史 Pod / 资源明细。设计必须保证：

1. **不落分钟 / 小时原始点或小时事实表；日摘要有不可续期的过期时间。**
2. **汇总失败不能把短期明细永久扣住。** 到期保存不完整 / 缺失状态，而不是无限等修复。
3. **独立清理，不依赖采集成功、账号活跃或页面是否有人访问。**
4. **清理异常时自动暂停新增明细，不能一边报警一边继续堆积。**
5. **采集、汇总、清理、告警一起上线。** 没有跑通清理演练，不允许打开正式采集。

不新增原始响应对象存储、候选清理表、软删除副本、历史物化版本或永久 quarantine。
也不把被删明细打包搬到 COS / GCS，制造另一处需要清理的垃圾。

## 2. 数据量：流量和存量分开算

旧小时方案及含个人维度 / 磁盘预留的日方案均已废弃，不能直接当作当前日级预测，也不能简单除以 24。

| 指标 | 日方案当前口径 | 解释 |
| --- | --- | --- |
| 消费日行基数 | 待测 repo + 稳定 Job + 资源类型 / 规格实际组合 | 多个 Pod 合并；不含个人 / project 必需维度或 build / Pod 随机值 |
| 资源日行基数 | 待测存活 / 已销毁资源每天实际出现数 | 原生节点高 churn，不能只拿当前存活数 × 天数 |
| 辅助证据 | 只存日重算必需的 UID / repo / Job / requests / 节点区间 | 不复制个人归属、磁盘 / PVC 关系、完整对象或 Pod 使用历史 |
| 体量参照，非最终方案 | 去掉磁盘后，若仍一 Pod-day 一行，日摘要约 33 万 / 月，辅助约 31 万 / 月，合计约 64 万 / 月、14 天约 30 万保留行 | 根据既有抽样构造；不是去个人后的稳定 Job 基数实测或严格上界 |
| 重算写入 / 删除次数 | 待四次日重算 canary 测量 | 每次按日覆盖，不能沿用旧小时模型的 mutation 次数 |
| 数据 + 索引初步预留 | 1–2 GiB，待 bytes/row 校准 | 不是物理配额或实际磁盘测量 |
| 长期账号周摘要 | 约 500–1000 行 / 年 | 不带 Pod、资源、个人、job |

关键不是某个假定数字足够小，而是**日行和辅助证据都有过期回收、容量门禁且无永久副本，存量不能随月份线性累积**。
业务日组合、实际保留行数与索引体量要测量；下文保留 200 万行 / 8 GiB 停写门限作为防失控 guard，不把门限当正常预测。

## 3. 每类数据的寿命

时间口径：Asia/Shanghai 周一 00:00 开始，持久化比较使用 UTC。
定义某周开始为 `W`，结束为 `E = W + 7 days`，硬过期为 `D = E + 7 days`。

| 数据 | 规则 | 到期处理 |
| --- | --- | --- |
| 云端返回的分钟 / 小时点与完整响应 | 只在有界计算中处理 | 计算结束释放，不入 DB / 对象存储 / 完整日志 |
| 资源日、消费组合日、固定 rollup 日摘要 | 归属于 usage_date 所在周 W；`expires_at = D` | D 后分批物理 DELETE；无小时表 |
| 日重算必需的标签 / requests / 规格 / 关联区间 | 按周切片，与引用的日摘要同周、同 D | 日行删除后，删除该周辅助证据 |
| 已删除 / 已结束 Pod 与资源的必要证据 | 与对应使用周相同，不额外延长 | 不因 enrichment 续期；不另存逐 Pod 使用事实 |
| 仍存活的资源 | 只在确认当前周仍活跃后建立当前周基线 | 旧周片段正常删除，不保留一条永不过期的 open interval |
| 历史账号周汇总 | 同业务键覆盖更新，长期保存 | 不保留每次重跑的 generation / 旧发布副本 |
| 任务状态 | 固定 job / account 状态行，覆盖更新 | 仅保留小型水位、计数与最近错误，不追加每 Pod 状态 |
| 新任务的 Job / Pod / 调试数据 | successful history 1、failed history 3；完成对象 TTL 建议 24h；新增诊断日志策略 7 天 | 同部署 / 日志平台一起配置，不能默认无限保留 |

例如 2026-11-16—22 的明细：2026-11-23 起只供补采 / 核对，**2026-11-30 00:00 北京时间硬过期**。
从 `usage_date` 当日 00:00 起算，该周周一至 D 为 14 天、周日至 D 为 8 天；若从各日结束的次日 00:00 起算，则分别为 13 天、7 天。两种表述使用同一个固定 D；不是每条日行都固定保留 14 天，也不是“每次更新再续 14 天”。

### 模型必须支持清理，而不是以后补

两张新明细表均要求：

- `id` 主键，`week_start`、`expires_at` 为 NOT NULL，UTC 过期值由统一周界函数生成。
- 全表过期索引 `(expires_at, id)`；周汇总所需的 `(vendor, account_id, week_start, scope, ...)` 索引。
- 日表以 `usage_date` + scope + 稳定资源 / 消费组合唯一识别，包含固定 `account_class` scope（vendor + account_id + resource_class）；字段为 CPU / memory / requests 宽行，每个指标字段组内联保存主设计 §4 的 `(namespace, metric, period, source_stat, unit, semantic_version)` 及分母契约。不将 Pod / build 编号放进稳定 job key，不按每 metric 拆行。重算、补标签不插入新 materialization version。
- 每日发布必须删除该日旧组合后写入完整新结果与 checkpoint，在经过 canary 验证的有界事务中原子提交；仅 upsert 会留下已消失的旧组合。大到无法安全原子替换时先停止该日发布并评审，不悄悄增加无清理的 staging / generation。
- `expires_at` 由使用周决定且不可因 UPDATE 改晚；数据输入没有合法使用时间则拒绝，不默认填“今天”。
- 新增表不继承 cost unmatched 的历史保留语义；不修改既有账单、CI lifecycle 或资源 serving 的保留策略。
- 迁移时就创建上述索引；在目标 TiDB 版本验证查询计划，不依赖未验证的 CHECK / TTL / 分区行为。

不为每轮扫描追加相同元数据：只有规格、归属、requests 等实际发生变化才新增区间，`observed_at` 更新本身不算业务变化。
只支持已保存的 repo、稳定 Job、资源类型 / 规格等约定维度，不承诺任意原始 label 事后重切；只存实际组合和固定 rollup，不展开笛卡尔积。标签证据只允许 repo / Job / 规格关联所需字段，不复制 author / owner / 个人邮箱 / roster / 全量 labels。必要证据初始上限 8 KiB / 区间，按 schema 校验，不静默截断资源 ID / repo / Job。超限标记证据缺口，不无限复制 JSON；完整 annotations / API 对象不写入这两张表。

## 4. 周汇总不能成为永久阻塞清理的理由

### 正常路径

1. 每次成功发布日摘要后更新该日期所属周的账号汇总（包括上一周和合法重试影响的周，不只当前周）：只读取 `(vendor, account_id, resource_class)` 的 `account_class` 日 rollup（由去重物理机器层预计算），按类别合并日积分、取同 scope 各日日峰值最大值。逐指标核对周固定的完整来源 / 分母契约；不相容日指标计缺口，不混加资源叶子或 Pod 消费 scope，也不相加不同类别的峰值。
2. **独立 15 分钟维护任务**依据采集契约 / 日历，在 E+48h 到期后的轮次生成阶段性 coverage 周结果，记录 `quality_checkpoint_at`，失败则后续轮重试；不依赖本周仍有日发布触发。D 前成功的合法日重试继续刷新其所属周，阶段性结果不是冻结。补采仍受明细窗与已验证源可读窗交集约束；源点不可读时只用最后可信日行，保留 stale / missing 和缺口，不改用粗粒度统计。
3. 到 D 执行最终收口事务：**先获得该周 guard / 写入边界，再读取有界 `account_class` 日摘要计算各资源类别最终结果**，不扫描资源 / 消费叶子事实或重读云端分钟点；同事务发布最终汇总 / 状态与关闭水位。不能先计算、后加锁发布，否则可能漏掉期间最后一次提交。失败则整体回滚；使用 DB 当前时间和当前锁定读，不允许长事务旧快照越过 D。
4. D 后自动和人工 writer 均不能再写入该周明细；独立 sweeper 删除该周所有明细和元数据。

### 连整周一行明细都没有，也必须收口

固定账号状态需要持久化 `collection_start_week`、可选 `collection_stop_week`、启用的资源类别 / 指标 / 语义契约及生效边界、`finalized_through_week`。它独立于当前 inventory 和 `cost_sources.is_active`，不按 Pod 或每轮采集追加注册表。
维护任务先按日历和该契约枚举所有已到 D 的应采周 / scope，逐周有界推进水位，再扫描实际过期行。因此整周采集失败、某项指标从未落行、源停用且没有候选行，也会生成 `final_missing`，而不是在趋势里无声消失。
只有成功的清单 / 采集证据证明没有资源时，才能发布“无资源、分母为 0、利用率 NULL”的正常结果；没有观测证据不能当成空账号。契约真实变更才记录生效边界，不为重跑增加版本。

### 到 D 仍失败

优先尝试从已保存、契约相容的 `account_class` 日摘要按资源类别重新合并，不必重新扫描所有 Pod 或恢复小时表；源 horizon 不足的 stale / missing 日仍如实影响最终 coverage / 完整性。
如果仍失败：

- 已有可信周结果：保留已有数值，标记 `final_incomplete`，记录最后成功覆盖区间、coverage、缺口和原因。
- 从未生成可信结果：写 `final_missing`，指标为 NULL，不填 0、不编造完整周利用率。
- 最终状态必须涵盖该周应有的指标 / 资源范围；不能只关闭成功的那部分，却遗漏失败范围的明细。
- 提交上述状态后，**仍按 D 清理明细**。不得自动延期到“等修好再说”。

这是明确的业务取舍：发生长期失败时，宁可历史趋势有可见缺口，也不保留用户不需要的长期明细。
现有 cost D+3 / D+5 延迟及个人分账不得阻塞利用率日数据过期；本功能不依赖 roster / author / owner 解析。成本对比独立更新。

如果 DB 不可用，连最终状态也无法写入，就不执行删除，并让写入门禁保持关闭；恢复后先收口旧周、清理，再恢复采集。
**DB 故障时无法承诺按时物理删完，但可以防止继续新增堆积。**

## 5. 独立 sweeper：小事务、可重试、不漏冷数据

建议同一 jobs image 增加独立维护命令和 CronJob，**每 15 分钟运行**，不挂在 collector 的成功尾部。
以下是设计参数，最终以 canary 校准；不需要新服务或消息队列：

| 参数 | 初始值 |
| --- | ---: |
| 每批选择 / 删除 | 最多 1000 行 |
| 单次任务删除上限 | 5 万行，跨两张明细表合计 |
| 单次任务运行预算 | 5 分钟，先到先停 |
| 并发 | 同一维护任务不重叠；同周写入收口与清理受同一 guard 保护 |
| 处理顺序 | 最老过期周 → 日摘要行 → 同周辅助证据 |
| dry-run | 必须支持；只 SELECT 计数 / 最老截止时间 / 少量样本，不改变状态或执行 DELETE |

每批流程：

```text
固定本轮 DB UTC cutoff
→ 按持久化契约 / 日历生成到 E+48h 的阶段性 coverage 结果，并最终收口到 D 的应采周 / scope；两者均包括没有任何明细的周
→ 确认最老实际过期周已经完成最终状态发布；没有则先收口该周
→ 利用 expires_at 索引，按 (expires_at, id) 取最多 1000 个主键
→ 短事务内按主键 DELETE，并重检 expires_at <= cutoff、week_start 与关闭边界
→ 同事务更新删除计数 / 保留行计数
→ 提交、让出资源，继续下一批，直到行数或时间预算耗尽
```

- 不用 OFFSET；不读取完整标签 JSON；不做一个跨数十万行的大 DELETE / 大事务。
- 每次从**当前最老剩余候选**重新开始，失败重试天然幂等；不能只记录一个永远前进的 ID 游标而漏掉之前残留。
- 扫描本功能拥有的两张明细表的全部过期行，**不 JOIN `cost_sources.is_active`**。账号停采、资源已消失、标签已匹配、某周没有新数据，都不能使旧数据漏清。
- 必要证据只能在引用它的同周日摘要清空后删；跨周不共用同一证据区间 ID，从模型上避免“永远被引用”的残留。
- 只允许操作明确白名单新表，不开放任意表名 / WHERE 的通用删除接口，不使用 TRUNCATE、级联删账单或对象存储清理。
- 清理状态仅保存计数、最老截止时间、最后成功时间、最近错误等小型字段，不把候选 ID 全部保存成另一个永久 manifest。

最终 repo-Job-资源日基数未测，不能沿用旧小时方案。仅按去磁盘后的逐 Pod-day 64 万 / 月参照，一周约 15 万行到期，5 万 / 轮约需 3–4 轮、约 1 小时；2 倍规模约 6–7 轮、约 2 小时。
这是参照任务满足预算时的追赶目标，不是正常基数保证或未压测性能承诺。canary 用实际组合基数及压力规模验证：追赶能力必须大于新增速率，未达标不能正式上线。

TiDB 原生 TTL 可在版本 / 行为验证后作为补充保险，但不是首版必要依赖；异步 TTL 也不能替代最终状态、写入截止、清理观测和停写门禁。

## 6. 防止“删完又被补采写回去”

所有 writer，包括定时采集、watcher 补元数据、手工 replay、历史回补，都必须遵守同一个入口约束：

- 只允许写当前周 / 未过期的上一周，且不得写已最终关闭的周。D 后新旧 worker 都必须拒绝旧周写入。
- 使用业务使用时间归周，不能以 `created_at` / `updated_at` / 本次入库时间归周来规避过期。
- 周收口、整日覆盖发布、辅助证据提交与清理使用一致的 guard；先在外部读取云 API，提交前重新检查时钟、usage_date 所属周、关闭水位和净行数预算。不能在持锁事务中等待云 API。日替换回滚必须同时恢复旧组合与计数，不能误删辅助证据。
- 仅有 Kubernetes `concurrencyPolicy: Forbid` 不足以阻止人工并发；需要 DB 层同一 guard。现有 `mark_job_started` / checkpoint 并不是互斥锁，实施时必须补齐并发协议。
- 历史回补超出明细窗口时，若来源尚可读，只允许流式生成周汇总；不得重新落下几个月 Pod 明细。无历史证据就写缺口，不从当前标签重建。
- 对成功日期只常规重算当天 / 前一天，该日期最后一轮为次日 18:30；之后迟到 repo / Job 证据不自动触发归属重切，unknown 和证据截止时间按最后可信版本展示。失败日期重试或显式有界 repair 仍受 source horizon、证据、保留窗和 fence 限制，不能从未保存或已清理的 Pod 使用量回推。
- 暂停 / 删除 collector 时仍保留维护任务，直到该功能明细全部清空；停采不是停清理。

### 长期存活对象不成为另一种垃圾

观察区间按周切片。新周基线需要当前 LIST / 观测确认同一 UID 仍活跃；不把所有历史 open interval 无条件复制到新周。
无法确认的对象保持 unknown / stale，不伪装成活跃；当前有使用量但身份不明的资源仍计入对应覆盖缺口。
既有旧周片段照常过期，所以即使结束 / 删除事件永久丢失，也不会因 `valid_to IS NULL` 永久保留。
当前没有磁盘 / PVC 状态链路，不维护 `unattached_since` 历史。计算资源只保留当前日重算需要的有界状态，不为保留连续性引入无限状态历史。

## 7. 清理失败：不仅告警，而且自动停写

独立维护任务之外，writer 在每批提交前检查维护健康与保留预算。以下为初始门限，调整需要审阅，不自动上调：

| 条件 | 动作 |
| --- | --- |
| 没有初始化成功的维护状态 / 未证明清理可用 | 禁止首次正式采集 |
| 最后维护成功距今超过 1 小时，或最老过期数据超过 D + 2h | 告警并优先恢复维护；不自动扩容 |
| 最老过期数据超过 D + 4h，或维护成功距今超过 4 小时 | **暂停所有新增利用率明细**，维护 / 最终汇总仍运行 |
| 两张短期表合计保留行达到 100 万，或两表数据 + 索引合计观测字节达到 4 GiB | 容量预警，检查流量、索引、标签区间和清理效率 |
| 两张短期表合计保留行达到 200 万，或两表数据 + 索引合计观测字节达到 8 GiB | **暂停新增明细**，不能只发告警继续写；不以仅 observation 表 / 仅索引体量替代 |
| 同时没有可靠维护状态和可靠计数 | fail closed，先校准再恢复 |

- 行预算覆盖两张新明细表；增删的计数与数据同事务更新，所有 writer 共用 guard，在窗口级原子提交前预留足够行数，不能先写再发现超限。
- 可以复用固定 `cost_job_state` guard 行持有小型计数 / 状态，但需要独立字段协议，不用它存按 Pod 无限增长的数组。
- 夜间用有界索引计数校准保留行数；两个新表规模已受限。计数漂移时暂停写入并修正，不使用长时间未更新的估计继续放量。
- 字节数从表 / 索引统计及 canary 每行实测跟踪。**8 GiB 是观测后的停写阈值，不是精确物理磁盘配额**，统计延迟、版本 GC、备份可能导致实际空间超过它。
- 自动恢复需同时满足维护健康、过期积压已清零、预算低于预警门限；保留暂停原因和缺失时间段，不能恢复时无界补写已过期数据。

监控必须至少有：每表保留行 / bytes、最老业务时间、过期行数、最老过期时间、每轮删除行 / 扫描行 / 耗时、最后维护成功时间、周最终状态、停写状态与丢失覆盖区间。
日常 health 检查要实际验证到期候选和进度，而不是“CronJob 启动过就算成功”。没有到期行的成功检查也要记录心跳。

## 8. 不把逻辑删除和账单空间下降混为一谈

DELETE 会产生索引维护、MVCC 旧版本、GC / compaction 工作，物理 / 计费空间不一定立即下降。
因此清理看板同时看：

1. 业务过期行是否已为零。
2. 表 / 索引和 DB 实际计费空间是否在合理周期内回收，或维持可复用高水位。

有逻辑空表但物理不回收时先核对 TiDB 计划、GC / compaction / 备份策略；不能自动执行危险 DDL / 手工改 GC。
备份使用既有平台有限保留周期，不为这些临时明细新增永久备份。整库恢复后先禁用 collector，重新执行维护门禁与过期回收，避免复活过期数据。
清理读写必须计入新日流程的 DB 预算；旧小时模型的 RU 假设不直接沿用。若实测吞吐 / RU 超预算，应调整批量、任务资源或保留策略，而不是悄悄取消清理。

## 9. 上线验收：必须包含过期与故障演练

使用隔离测试库 / 测试时间，不对生产造数或试删：

- 连续模拟至少 6 个周周期：明细只包含允许的两个周，row count 不随累计周数线性增长；周汇总保留全部 6 周。
- 宽限到期、时区周界、更新不续期；明确断言周一 / 周日日行从当日 00:00 到 D 分别为 14 / 8 天、从各日结束起为 13 / 7 天。活跃跨周对象存在新周基线，旧周没有悬空引用。
- 模拟云端 60s 点可读期短于明细保留期、契约不匹配及日期失败：不越界重放或用粗粒度值覆盖最后可信日行，stale / missing 影响完整性；各类别周结果只从相容 `account_class` 日行收口，不依赖叶子行扫描 / 云端重读，D 不延期。
- 汇总连续失败到 D：产生 `final_incomplete` / `final_missing`，旧周仍可清空；repo / Job 解析失败只形成对应缺口，个人字段 / cost 不构成清理依赖。整周零行、某 scope 零行、源已停用仍能按契约收口；有证据的空资源与采集缺失必须区分。
- 最后一个 writer 与最终汇总并发：先获得 fence 后读取的结果包含所有 fence 前提交；最终状态和关闭水位原子发布，旧快照 / 客户端旧时钟不能绕过截止。
- 没有新日发布仍由维护任务生成 E+48h coverage checkpoint；上一周合法晚重试刷新所属周而不是仅当前周。成功日期次日 18:30 后迟到关联不自动重切，状态 / 截止时间可见。
- 容量门禁同时计入两表数据和索引；构造只有 daily 表大、只有 observation 表大、数据大而索引小的场景，4 / 8 GiB 均按合计正确触发，不能漏掉非索引数据。
- 清理中途退出、事务失败、重启、清理预算耗尽：重复运行无漏删 / 错删，预算计数守恒。
- 停采账号、删除源配置、没有新数据的周、丢失 Pod 删除事件：依然能过期清空。
- 过期批次与手工 replay / 长时运行旧 collector 并发：关闭边界生效，不能重新插入已清理周。
- 清理任务停掉 / 无权限 / 慢查询 / DB 故障：4h 门禁阻止新增，不只是报警；恢复后先回收再开放。
- 行数上限、字节预警、元数据高频变化、重复扫描、超大 label、唯一键重算：不出现不受控新增。
- `EXPLAIN` 证明过期选择走 `(expires_at, id)`，删除只触达小批主键；用实际业务日基数及压力规模演练。实测前可用逐 Pod-day 参照的约 30 万保留行和 2 倍规模做初步测试，不把它当作最终容量保证。
- 四次日刷新与清理并发、当天 partial、分窗端点去重、同日重算不累加、旧组合消失与标签变化：日发布原子回滚，证据引用和计数无残留，最终范围内没有小时事实表。
- 检查原始响应、临时文件、Job、日志、错误样本和任务状态，不存在绕过 DB 清理的永久副本。
- `--dry-run` 结果与实际小批回收一致，且 dry-run 不修改业务表或任务水位。

发布门槛：上述测试 + 周切换演练通过，维护 CronJob / 告警 / writer 门禁先就绪，再启用 collector。
用户验收要看到“旧周到期后明细为零、周趋势还在”的结果，而不只是当前周页面正确。

## 10. 现有代码可复用的部分与边界

`sync_gcp_unmatched_resources.py` 已有按主键小批删除、删除前重检谓词的模式，可以参考，不应重新拼一个大 DELETE。但其 `write_unmatched_resource_rows` 把多轮删除和 upsert 包在同一个外层 `engine.begin()` 中；**只能复用查询形状，不能照搬事务边界**。新 sweeper 的 1000 行必须是独立提交的小事务。
但“某次导入覆盖了旧行时清 superseded”与“无论源是否活跃都清过期数据”是两回事，不能用前者替代本设计的全局 sweeper。
`state_store.py` 提供 checkpoint，可复用事务内保存计数；它当前没有自动提供上述互斥 / 容量门禁。
本设计不把此前 unmatched / COS 遗留问题归因于某个未经调查的单点，也不在本次修改或清理其线上历史。
