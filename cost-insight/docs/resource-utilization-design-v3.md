# 腾讯云资源利用率 V3：历史机器与按业务标签汇总的 Pod 利用率

状态：设计记录，未实施。基于 [V2 已确认边界](resource-utilization-design-v2.md#16-业务确认收口与统一实施边界)。本记录不改变账号范围、原有成本事实和归因，也不授权迁移、部署或启用采集。

## 1. 优先验证：复用现有腾讯账单 importer

现有 importer 已调用 `DescribeBillDetailForOrganization`，并将计费组件写入 `cost_bq_export_summary_daily`。这个表保留账号、地域和 `resource_name`（优先用 `ResourceId`，缺失时退回显示名），可辅助发现机器候选，但不能直接用于 V2 的窗口规划：`usage_date` 只有 `FeeBeginTime` 的日期，`source_export_time` 是 `PayTime`；精确的计费起止、CVM 账单机型和 TKE 节点的 `UsedAmount` / `UsedAmountUnit` 没有作为可读字段保留。离线验证中，同一个节点组件将计费结束时间从 12:30 改为 12:45、CPU 数量从 8 核改为 16 核，其余字段不变，导出的成本记录完全相同。腾讯 COS 对象并非已验证来源。

**候选方案**：在现有 importer 首次拿到原始页时提取真实资源 ID、账号、地域（必要时加 cluster）和计费起止，供 planner 发现历史机器和限定查询窗口。按 §4 的新口径，机器利用率不需要历史规格，也不查询实例当前规格。读取以账号和 `BillDay` 分区为单位；只有本次扫描完整结束才发布这份证据，不以有成本行、最大完成日或 D+5 计数相同代替完成/内容证据。规划以真实计费时间切分北京时间使用日，跨月也不能漏；调度看已完成分区和剩余回放时间，不假设早上的 planner 已拿到当日下午才导入的分区。先验证再决定持久化方式，不预先新增表或跨云框架，利用率证据发布失败不改变原账单或分摊结果。

**账单修订**：账单只负责发现，缩短或撤销账单区间不自动撤销已经真实观测到的机器读数。只补仍可回放、能确认未被处理的新分钟；重叠或契约冲突且不能证明增量安全时不自动相加，记录待人工核对。不要仅从日行的和、计数和峰值反推应撤掉的窗口。

**验收**：在单独授权的 canary 中，用同一份完整账单样本（包含已退出节点、跨日计费和重复计费组件）对比完整 API 读取与 importer 路径产生的去重机器集合及查询窗口；验证未完成分区不会被规划，迟到或修订数据不会重复累加。实测 API 调用数、查询耗时、TiDB RU，以及导入完成到监控回放截止之间的余量，再决定是否切换。若腾讯验证通过，AWS/GCP 可各自从现有详细账单导出提供同样的发现证据，复用窗口规划；不要求共用成本日表，也不替代各云监控查询。

参考：[腾讯账单字段映射与导入协议](tencent-billing-import-design.md)、[当前导入字段投影](../src/cost_insight/sources/tencent_billing.py#L179)。

## 2. 修复：V2 直读账单不能仅凭 `Total` 停止分页

**已离线复现**：[V2 `billing_candidates`](../src/cost_insight/utilization/tencent.py#L394) 在 `offset == Total` 时退出。账单 importer 的设计已注明 `Total` 可能是旧的缓存值。模拟某产品实际有 101 条账单、`Total=100` 且首批返回满 100 条时，V2 不请求 offset 100，最后一台机器不会被规划；在 V2 还会漏掉其应采覆盖率分母。

**最小修复**：只要 V2 直读路径还存在，就不能用 `offset == Total` 判定结束。验证该产品过滤查询遵守现有 importer 的短页结束契约；在此基础上，满页继续翻页，`Total` 仅作审计或异常信号，不作完整性证明。保留扫描上限、重复页等保护；到达上限仍无法确认结束或分页异常时，不返回部分候选。添加 `Total=100`、实际 101 条的回归用例，断言 offset 100 被读取、尾页机器进入候选；另测异常或超限不会产出部分结果。若 V3 完全移除这条直读路径，则不保留带缺陷的 fallback。

## 3. Pod 利用率按来源独立开关

Pod CPU / 内存利用率可按来源或集群独立启用（建议配置名 `pod_collection_enabled`），默认关闭，独立于机器采集和报表开关。只有已有 Pod 监控来源、且验证了指标、历史 selector 和可回查窗口的来源才显式启用。不为缺少数据源的 AWS / GCP 集群新建采样器，也不要求所有云都提供 Pod 数据；本阶段仍只接入已确认的腾讯账号范围。

- **关闭**：不启动利用率专用的 Node LIST，不写新的 Pod 采集上下文，不规划新的 Pod 窗口；没有既有 Pod 任务时，不要求配置或验证 Pod 指标契约，也不调用 Pod 监控 API。机器采集和原有 Pod 生命周期 watcher 照常运行。
- **从开到关**：用 DB 时钟记录关闭生效时间，从该时刻停止增加证据和新规划。已登记任务按原契约、不可变上下文和截止时间收尾；关闭前已确认但未规划的完整分钟由维护按缺测补入仍在保留期内的分母，关闭后的分钟不计入。回收前检查规划尾段和关联任务都已结算。原契约保留至收尾完成，首版不引入并行契约版本；旧工作集排空后再重开或换契约，不把停采期间当连续观测。已产出的 workload 统计按原保留期自然过期。
- **API / UI**：未启用的来源不返回新 Pod 测量值；页面可隐藏 Pod 区域，或标明「未启用 Pod 采集」。不填 0%，不计为缺测或采集失败；已启用期间的缺测仍按原口径表示。

**验收**：用不含 Pod 契约的 profile 验证机器链路可独立运行，无 Node LIST、Pod 上下文、新 Pod 任务或 Pod 监控请求；验证关闭后既有任务有界收尾，且 API / UI 区分「未采集」、实际缺测和观测到的零用量。

### Pod 上下文只存云实例 ID，不用 IP 兜底

`pod_utilization_context` 用一列可空的 `node_instance_id` 替换 `node_query_kind` / `node_query_value`。存观测该 Pod 区间时有证据支持的云实例 ID，例如 `ins-abc123` 或 `np-4zrtq925-7w4j5`；腾讯查询用 `un_instance_id`，并带集群、namespace 和 Pod 名。不依赖该机器是否被账单发现。取不到可信 ID 就存 `NULL`，不发监控查询；已启用期间确认应采的分钟仍计入覆盖率分母，不记为零。只在身份重新确认生效后用于新区间，不用事后的映射回填旧区间。

**依据**：[腾讯指标文档](https://cloud.tencent.com/document/product/248/53821)列明 Pod CPU 和内存指标均支持 `un_instance_id`，[既有实测](tencent-utilization-validation-and-cost-estimate.md#2-已验证的端到端链路)也已按实例 ID 查到两种指标。现有按 `nodeName` 缓存的映射在 IP 复用时可离线复现错绑：刷新前新 Pod 被映射到旧实例 ID，刷新后才返回新 ID，清空缓存又退回裸 IP。因此不能只删 IP 兜底，还必须拒绝仅凭陈旧的 `nodeName` / IP 映射写入实例 ID。

**回归验收**：模拟两个实例复用同一 IP、Node 缓存尚未刷新，新 Pod 不得绑定旧 ID；Node 映射失效且 Pod 只收到 BOOKMARK 时，不得继续延长旧身份。缺 ID 不发查询；身份确认后只对新区间用正确实例 ID 查询 CPU 和内存。Canary 记录身份确认延迟及不同运行时长的 Pod 中未解析的比例；不能只验证错绑消失、不检查短 Pod 是否普遍失去有效观测。

## 4. 机器日统计：只用历史监控 API 的分钟百分比

`machine_utilization_daily` 仍是一台可识别机器 × 一个**北京时间自然日**，CPU / 内存同行。账单只负责发现机器和规划查询窗口，不是监控读数或使用率分母。对于普通 CVM 和 TKE 原生节点，使用腾讯历史监控 API 的有效 60 秒平均百分比；没有机器规格不影响该百分比的有效性。不查当前 CPU / 内存规格、不用账单规格将百分比换算成绝对用量，也不从 Pod requests 或 usage 推算整机利用率。

- **只有真实观测才写日事实**：当天 CPU 和内存都没有有效点就不建日行；只有一项有点，就保留该行，另一项显示 `N/A`。API 返回的 `0%` 是有效观测；`null`、无点和失败不是零。任务超期不为机器生成空结果，也不能推进有效观测的时间；失败在既有任务或运维日志中排查，不为此增加长期明细表。查不到日行只代表没有已保存的观测，不证明机器不存在或空闲。
- **只保留 6 个统计列**（拟名）。每个指标独立聚合，`sample_minutes=0` 时 `percent_sum=0`、`peak_percent=NULL`，不计算或展示 `0%` 均值。

  | 列 | 存什么 | CPU / 内存样例 |
  | --- | --- | --- |
  | `cpu_percent_sum`、`memory_percent_sum` | 各有效分钟百分比读数之和，单位为百分点 | CPU `[50, 25]` → `75`；内存 `[0]` → `0` |
  | `cpu_sample_minutes`、`memory_sample_minutes` | 去重后的有效一分钟读数个数 | `2` / `1` |
  | `cpu_peak_percent`、`memory_peak_percent` | 观测到的最大一分钟平均百分比 | `50` / `0` |

- **查询口径**：日均值 = 百分比之和 ÷ 有效分钟数；同一台机器跨天先分别加总两列再除，不能平均每日均值。跨天峰值取各日峰值最大值。可展示有效分钟数，但不称为覆盖率，也不暗示观测覆盖全天。不是瞬时峰值，不存峰值发生时间。
- **取舍**：每个有效分钟权重相同。若前 30 分钟为 4 核 / 50%，后 30 分钟为 8 核 / 25%，本口径报 `37.5%`；按容量加权才是 `33.3%`，本版不计算后者。不跨不同规格机器推算资源池容量加权利用率，也不做组峰值。

这替代 V2 机器表的 22 个指标统计列：不再保存绝对用量、匹配或应采容量积分、应采/匹配/未知/零分母秒数、峰值时间等。机器的简化不改变 Pod 的缺测与未知 requests 语义；workload 见 §5。

**验收**：用不带规格的历史机器样本验证 CPU / 内存独立的观测与零值、两项全缺时不建日行、不同样本数的多日聚合，以及重复投递不会重复累加读数。

## 5. Workload 日统计：采集到 Pod，按来源配置业务标签

机器报表用于发现物理资源是否闲置，但 CI Job 与机器池不是一一对应。Pod 历史监控用量与该时段的 requests 匹配后，按业务标签汇总，用于找出哪些业务的 requests 值得检查。它不表示某个 Job 导致了机器闲置，也不分配机器使用量或成本。保留 `workload_utilization_daily`，是为了在逐 Pod 上下文回收后仍可看近期业务统计，不是为了查询单个 Pod。

**标签由来源配置，不写死在表或 API 里。** 每个接入来源显式选择允许汇总、筛选或分组的非个人标签键。CI 可选 `repo`、稳定 `job`，可用明确的 `team` 标签或已有业务归属映射看团队；不以 `author` 为统计维度。键名通过白名单不代表值稳定：Job 用已验证的稳定路径或来源映射，不能靠排除几种数字样式猜测原始值不是执行 ID。未来 QA 可选择 `test_project`、`test_plan`，或表示可重复任务的执行类型。若「测试执行」指某次执行的唯一 ID，像 CI 的构建编号一样，本版不纳入持久化汇总；即使不存 Pod UID，这类标签也可能把汇总变成逐次执行明细。QA 只是复用示例，本阶段不扩大接入账号范围。标签缺失不丢弃用量，在按该标签分组时显示为「未标记」。

### 日表：29 列精简到 11 列

一行 = **账号 × 北京时间日期 × 已批准标签组合**，用 `(account_id, usage_date, group_key)` 唯一标识。V2 的 CPU、内存 requests 档位从分组粒度移除；写入时按该 Pod 当时的 requests 计算贡献，再并入标签组。按日保存是为了在 Pod 上下文回收后仍能按任意日期范围查询和按日过期；不存每日百分比或 Repo、Job、测试项目各自的汇总副本，也不建周表。只保留当前和上一北京时间周，查询和有界批量清理从 `usage_date` 推导保留边界。

| 保留列（拟名） | 存什么 | 示例 |
| --- | --- | --- |
| `account_id` | 来源账号 | `100050658403` |
| `usage_date` | 北京时间使用日 | `2026-11-20` |
| `group_key` | 规范化标签组合的哈希，不含 requests | `sha256(规范化标签)` |
| `labels_json` | 供筛选和分组的业务标签 | `{"repo":"pingcap/tidb","job":"unit-test"}` |
| `cpu_used` | 匹配分钟的 CPU 实际用量积分 | `2700` 核·秒 |
| `cpu_requested` | 同一批分钟的 CPU requests 积分 | `5400` 核·秒 |
| `memory_used` | 匹配分钟的内存实际用量积分 | `4800` GiB·秒，库内存字节·秒 |
| `memory_requested` | 同一批分钟的内存 requests 积分 | `9600` GiB·秒，库内存字节·秒 |
| `cpu_matched_pod_minutes` | CPU 有观测且 request 为正的 Pod·分钟数 | `45` |
| `memory_matched_pod_minutes` | 内存有观测且 request 为正的 Pod·分钟数 | `40` |
| `expected_pod_minutes` | CPU / 内存共用的应采 Pod·分钟数，不是墙钟时长 | `60` |

**查询口径**：每个指标只把有观测且 request 为正的分钟纳入用量和 requests 积分。跨天或标签组先分别求和，再计算 `SUM(used) / SUM(requested)`，不平均各行百分比；没有有效分母显示 `N/A`。有效时间覆盖率为 `SUM(matched_pod_minutes) / SUM(expected_pod_minutes)`，不是容量覆盖率。例中两个 Pod 各应采 30 分钟，CPU 平均使用率 50%、覆盖 75%，内存平均使用率 50%、覆盖约 66.7%。已启用采集期间的已确认应采分钟即使缺测，也计入覆盖分母，不把缺测填成零用量。首版不维护实时全量分母：当查询所选日期仍有已确认但未结算的任务或尾段时，将结果标为 `partial`，覆盖只描述已结算范围，不能将其显示为完整日期覆盖。部分状态可按来源级保守提示，不增物化表。

**删除**：自增 `id`、精确 `cpu_request_cores` / `memory_request_bytes`、`quality_json`、`cutoff`、`updated_at`、`expires_at`；不再另存 `*_total_used`、`*_usage_seconds`、`*_expected_capacity`、`*_unknown_seconds`、`*_zero_seconds`，两套 `*_expected_seconds` 合成共用计数。采集时仍区分未知 requests 和已知零 requests，但首版不单独展示这两类诊断，也不报告无有效 requests 的绝对用量、容量覆盖率或组峰值。

**验收**：CI 可按 Repo 过滤、按 Job 分组；同一 schema 和查询入口可用离线 QA 场景按测试项目过滤、按测试计划分组。相同标签而 requests 不同的 Pod 仍合入同一行且加权结果正确；缺标签的用量仍可见；单次执行 ID 或个人标签不会落入业务事实。

## 6. 采集任务：15 列精简到 13 列

`utilization_task` 是短期任务、待投递记录和完成断点，**一行 = 一个机器或 Pod × 一个历史窗口**，同时采 CPU / 内存；不是每条 Kafka 消息一行。Kafka 只传 `task_id`，不保存任务状态或业务数据。继续复用腾讯侧 Kafka，不另建 outbox 或采样结果表。

| 保留列 | 存什么 | 示例（时间均为 UTC） |
| --- | --- | --- |
| `id` | 由账号、对象身份、窗口和采集契约确定的稳定任务 ID | `sha256(…)` |
| `account_id` | 来源账号，用于隔离、查找待调度任务 | `100050658403` |
| `kind` | 选择机器或 Pod 的查询、写入和过期规则 | `pod` |
| `context_id` | Pod 的历史上下文版本引用，机器任务为空 | `1042` |
| `payload_json` | 只存上下文引用无法提供的任务参数 | Pod：`{"contract_version":"…"}` |
| `window_start` | 应查历史窗口起点，包含 | `2026-11-20 04:00` |
| `window_end` | 应查历史窗口终点，不包含 | `2026-11-20 04:10` |
| `due_at` | 首次可采或失败后下次可重试的时间 | `2026-11-20 04:20` |
| `deadline_at` | 固定采集和提交截止，不因重试续期 | `2026-11-21 04:10` |
| `status` | 待处理、领取、重试、已完成或已过期 | `running` |
| `lease_token` | 本次领取的凭证，阻止旧 worker 提交 | `8e5f…` |
| `lease_until` | 领取失效时间，之后可接手 | `2026-11-20 04:25` |
| `dispatched_at` | broker 确认投递的时间，用于控制重发，不代表完成 | `2026-11-20 04:20:01` |

**删除与去重**：删除 `updated_at` 和 `attempts`。第一次可采仍等待来源上报，后续用固定、有界的重试间隔更新 `due_at`，不按尝试次数终止。Pod 身份、`node_instance_id`、requests、业务标签只从已引用的上下文版本读取，不为每个窗口复制；上下文的业务快照不得被后续观测改写，有未完成任务时不得回收。机器任务没有上下文，JSON 只留规范机器 ID、地域、必要的集群和机器类别、采集契约版本，不留规格或多余账单快照。任务不存原始响应、结果副本或逐次尝试历史。

**事务和回收**：先落任务再投递，收到 broker 确认后更新 `dispatched_at`；worker 提交时验证 `lease_token`、`lease_until` 和 `deadline_at`。日表贡献与 `done` 同事务，提交后才 ack Kafka。过期机器任务不补空日行；过期 Pod 任务须先原子计入仍在保留期内的已确认应采分钟，再转终态、回收。过期上下文的未规划尾段也须补记，不能漏算覆盖分母。迟到 Kafka 消息查不到任务时忽略，不能重建。planner 的限制另行保证：机器终态断点须保留到该使用日的合法规划窗口关闭，不能只按单条任务截止清理、却允许不同边界的任务重叠写入；该边界按使用日和上游回放契约固定，不被重试、重规划或换契约延长。Pod 依靠与入队或缺失结算原子推进的上下文游标防止重复规划。旧窗口的重叠和版本冲突默认拒绝自动累加，不另建永久去重流水。

**验收**：重复投递、提交后 ack 前崩溃、lease 到期后旧 worker 返回、任务和上下文回收后的迟到消息，不得重复入账；校验 Pod 任务在上下文续订或切段后仍使用引用的旧快照，过期缺失只计一次、暂停时维护照常运行。
